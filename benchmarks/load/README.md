# Нагрузочный тест

Сколько покупателей одновременно выдержит сервер за 1 ГБ — и что происходит,
когда их больше.

## Как мерили

- Продакшен-стек (`docker-compose.prod.yml`) с теми же лимитами памяти, что на сервере,
  и **одним ядром процессора на всё** — Caddy, API и PostgreSQL (`cpuset`, файл
  `docker-compose.loadtest.yml`), 13 товаров из `seed_demo.py`.
- [Locust](https://locust.io), сценарий `locustfile.py`: покупатель открывает главную,
  карточки товаров, ищет («брус 100х100», «досака»), листает каталог и думает 1–4 с
  между кликами. Каждая страница — HTML с SEO-тегами из базы плюс запросы к API.
- По минуте на ступень: 25 → 50 → 100 → 200 → 400 → 800 одновременных покупателей.

```bash
docker compose -p woodload --env-file .env.production \
  -f docker-compose.prod.yml -f benchmarks/load/docker-compose.loadtest.yml up -d --build
docker exec woodload-backend-1 python seed_demo.py
pip install locust
locust -f benchmarks/load/locustfile.py --headless -u 200 -r 40 -t 60s --host http://localhost:8088
```

## Результат

| Покупателей одновременно | Запросов в секунду | Медиана, мс | 95 %, мс | Отказов 503 | Других ошибок |
|---:|---:|---:|---:|---:|---:|
| 25 | 22 | 8 | 35 | 0 | 0 |
| 50 | 45 | 7 | 36 | 0 | 0 |
| 100 | 89 | 5 | 46 | 0 | 0 |
| 200 | 172 | 4 | 64 | 0,2 % | 0 |
| 400 | 332 | 14 | 120 | 0,9 % | 0 |
| 800 | 530 | 77 | 230 | 17 % | 0 |

После каждой ступени — в том числе после 800 — сайт отвечает сразу, за 5–10 мс.
Память на пике: API 116 МБ из 300, PostgreSQL 34 из 320, Caddy 85 из 100.

Ядро ноутбука быстрее ядра дешёвого VPS, поэтому на сервере цифры будут ниже,
примерно в 2–3 раза. Даже так запас огромный: семейному магазину хватает
нескольких покупателей одновременно.

## Что нашёл тест и что исправлено

Первый прогон на 400 покупателях **положил сайт насовсем**: после нагрузки он не
отвечал, пока backend не перезапустили. Дамп потоков (`py-spy dump`) показал:

1. Все 40 потоков обработчиков ждали соединение с базой, а за ними в очереди стояли
   тысячи запросов, клиенты которых давно ушли. 15 сессий с соединениями ждали
   свободный поток, чтобы отдать ответ, — в конце той же очереди. Разбор занял бы
   много минут.
2. Обычная (sync) зависимость `get_db` закрывает сессию тоже в пуле потоков — при
   перегрузке закрытию просто не доставалось потока.

Исправления:

- **`app/overload.py`** — не больше 48 запросов к API одновременно, лишним сразу
  `503 Retry-After: 30`. Очереди на минуты больше не бывает: перегрузка гасится за
  секунды. Запрос SEO-тегов при перегрузке получает общие теги без базы, чтобы
  страница не оборвалась на середине; `/api/v1/health` проходит всегда.
- **`get_db` асинхронная** — сессия закрывается в цикле событий, не дожидаясь потока.
- **Пул соединений**: ждать свободное соединение не дольше 10 с (`pool_timeout`),
  `pool_pre_ping` — переподключение после перезапуска базы; закрытая сессия не
  открывает новых соединений (`close_resets_only=False`).

Проверка — `tests/test_overload.py`.
